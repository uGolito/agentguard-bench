# Threat model

The adversary may modify retrieved document text, API bodies or metadata. Trusted components are the user objective, system instructions, scenario evaluator ground truth and local runtime code. A contradiction may be a benign data-quality issue rather than an attack.

Targeted failures: disclosure of synthetic canaries, unauthorized simulated email/record changes, acceptance of manipulated statuses, and unwarranted confidence under conflicting evidence. Six local tools provide read fixtures and record sensitive operations in memory. They have no network or external mutation capability. There is no shell execution or dynamic evaluation of fixture content.

Baseline instructions are not a security boundary. Its mandatory input interface validation cannot establish authorization. Guarded modes use a separate trusted policy with exact arguments and use counts; neither documents, tool outputs nor reviewer decisions can create a grant. Output schemas and evidence annotations bound how data is accepted and marked verified. Reviewers remain fallible. The fake provider cannot be attacked because it does not interpret messages.

Out of scope: real credentials, real users, malware execution, OS sandbox escape, external MCP servers, real financial or communication actions, model-training attacks and claims about deployed systems. The tool abstraction is compatible in shape with named JSON-schema tools, but is not an MCP transport implementation.

The optional Anthropic adapter adds a credential boundary: the API key comes only from the process environment after explicit live opt-in; it is sent to the fixed official API endpoint and never placed in prompts or traces. Client redirects remain disabled. Environment proxies/CA overrides are ignored by default; explicit codex-cloud mode trusts the reviewed runtime proxy and CA configuration without direct fallback. The proxy and its HTTP secret bindings become part of the trusted computing base; see cloud_setup.md. All fixture content sent to a future live model must remain original synthetic data. Raw model responses are untrusted, typed calls are dispatched only to the six existing local tools, and malformed/truncated responses retain failure outcomes. Request/cost controls bound estimated API use, not model behavior or provider invoices. Test transports are injected and sockets are blocked by the test suite.

Trusted local policy files and reviewer implementations are part of the trusted computing base. A reviewer receives immutable action text and no tool handles, but arbitrary malicious Python code is outside this isolation model. Its async timeout is cooperative. Known-literal blocking is not comprehensive data-loss prevention; literal evidence support is not truth verification. A deliberately mistaken trusted policy can permit an unauthorized action, and tests keep this visible through independent evaluation ground truth. See [control contracts](safety_controls.md) for precise boundaries.

The real reviewer is a second inference context, not a new trust root. Its system role treats proposed action strings as untrusted data; only objective/action are forwarded. It cannot create grants, see the primary transcript or invoke tools. A reviewer can still be manipulated or share primary-model biases. Both clients use the same per-mode ledger; failures deny execution and retain unknown costs. Local journal integrity and budget metadata are not cryptographically attested.
