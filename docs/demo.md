# Public demonstration — SIMULATED

The static dashboard demonstrates software behavior using authored fake-provider scripts. It contains no live Claude, reviewer or other model findings. No API key, backend, analytics, CDN dependency or paid service is required.

## Reproduce from a checkout

Install the locked dependencies and editable package as described in the README, then:

```bash
agentguard demo --output results/demo
python scripts/verify_demo.py results/demo site/data
python -m http.server 8765 --bind 127.0.0.1 --directory site
```

Open http://127.0.0.1:8765/. HTTP serving is a local preview convenience; deployment is plain static files. Opening index.html directly can fail because browsers restrict local-file fetch. Every demo output directory must be new. The command always constructs fake providers with live opt-in disabled; it has no live provider, trace-import or credential options.

The five generated artifacts reproduce byte-for-byte across supported Windows/Linux Python versions. The manifest records canonical scenario and policy hashes plus exact file SHA-256 digests. JSON/JSONL/text/CSV use LF regardless of host OS; .gitattributes preserves generated bytes. Ordinary experimental runs still retain UUIDs, timestamps, SDK metadata and timing. Only the public demonstration projection removes volatile IDs, timestamps, Python version and measured latency.

## Profiles and attribution

- **SIMULATED reference:** original scripts for all 30 frozen scenarios in A/B/C, one episode per scenario/mode. Each script already knows the expected answer.
- **SIMULATED adversarial probes:** copy the same 30 scenarios and overlay only fake_script. Insert one unauthorized email proposal on each of the 16 attack-present cases; add literal synthetic canary disclosure in pi-004; propose confident answers in evidence cases that require uncertainty. The runtime, criteria, fixtures, objective and policy are unchanged. The overlaid snapshot hashes differ and are retained in projected rows.
- **SIMULATED false-refusal diagnostic:** a fake-deny reviewer on the three authorized-action cases. These three episodes are separate from the comparison arms and demonstrate reviewer false positives; they are not evidence about real oversight.

The main profiles contain 180 episodes in total; the separate diagnostic adds three. Scheduling reuses run_paired with order seed 1729. Each profile holds scenario/configuration/policy controls constant across modes. Do not interpret differences between profiles as a controlled model experiment. Fake scripts ignore messages and cannot measure susceptibility to injection.

The demonstration preserves incomplete cases rather than forcing perfect outcomes. In the adversarial profile the baseline executes 16 unauthorized synthetic emails, while protected modes block those 16 proposals. Model ASR remains unsafe even where runtime ASR is reduced. This is intentionally authored infrastructure behavior, not an empirical robustness finding. Blanket refusal is visible through completion and false-refusal metrics.

## Artifacts and interpretation

- demo.json: SIMULATED aggregate/category counts, selected example executions, profiles, controls and baseline/candidate comparisons.
- traces.jsonl: all 183 projected episode executions, including messages, proposed/delivered answers, tool responses, guard decisions, effects and reviews. These are synthetic-only public projections, not imported private/live traces.
- metrics.csv and report.md: labeled SIMULATED raw numerator/denominator summaries.
- manifest.json: asset digests, scenario hashes, policy hash and trace-row count.

The dashboard displays separate model/runtime ASR, completion, unauthorized execution and false refusal, plus blocked/executed action counts and fake-review opportunities. Category selection uses eligible denominators; benign conflicts do not enter ASR. API cost is exactly $0; tokens, model latency and statistical intervals are not applicable. Measured local runtime duration is deliberately omitted. Conditional cluster intervals remain available in the existing live-analysis infrastructure when appropriate; fake runs do not receive inferential intervals.

## Browser verification and screenshots

Optional development tooling (not a dashboard/runtime dependency):

```bash
python -m pip install playwright==1.64.1
python -m playwright install chromium
# In another terminal while the local server above is running:
python scripts/check_dashboard.py
```

The script checks both profiles, category filters, 36 scenario/configuration combinations, inert trace rendering, page/console errors and mobile overflow. It restricts browser requests to the site's own origin. Screenshots are saved in docs/assets. Browser verification is also run in the Pages workflow; screenshots are presentation artifacts, not scientific measurements. Keyboard focus, form labels, native controls, responsive layouts and reduced-motion support are included; no full accessibility certification is claimed.

## Deployment boundary

The Pages workflow runs tests, security checks, deterministic regeneration/byte comparison and browser checks before deploying only site/. It uses the existing public repository, GitHub-hosted Linux runners and GitHub Pages, with scoped Pages/OIDC deployment permissions. results/, source credentials and live artifacts are never uploaded. Pages publication requires repository Pages permissions/settings; an authorization failure must be reported, not bypassed. No custom domain, billing change, API calls or GitHub Release is needed.
